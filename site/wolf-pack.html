What it reads

You cannot migrate what you have not found

An endpoint scan shows what your servers offer. Most cryptography lives deeper: a hash in a login module, a key size in a config file, an old OpenSSL inside a vendor binary. Wolf Pack reads all of it and hands you one list, in the CycloneDX format auditors and tools already accept.

  • Source code

    Python, Java and Kotlin, Go, JavaScript and TypeScript, C and C++, C#, Rust, Swift and PHP, including algorithm names passed into functions or built from pieces.

  • Configuration

    nginx, Apache, HAProxy, sshd, openssl.cnf, Spring properties, YAML, JSON, INI and TOML.

  • Cloud and Kubernetes

    Kubernetes TLS secrets and ingress annotations, AWS and Azure load-balancer TLS policies, and KMS key specs in Terraform.

  • Keys and certificates

    Including private keys that were committed by mistake, and certificates that outlive 2030.

  • Binaries, JARs and containers

    Algorithm constants, embedded OpenSSL versions and JCA names, also inside a saved Docker or OCI image.

  • Dependencies

    Manifests for pip, npm, Maven, Gradle, Go, Cargo and NuGet, checked against what the code imports.

  • Live TLS and SSH

    What each server negotiates, including whether it accepts hybrid ML-KEM groups.

  • Traffic captures

    TLS and SSH handshakes in a pcap file: what clients and servers really agreed, without touching them.

  • Other tools' CBOMs

    CycloneDX files from CBOMkit or another scanner can join the organisation inventory.

How it decides

Why it is called a pack

Scanners that match names drown you in false alarms. Wolf Pack splits the work so that finding and deciding are separate jobs.

01 · scoutsFind everything

Each scout reads one kind of source and deliberately over-reports. Missing something is worse than a false lead.

02 · denCheck the evidence

Mentions in comments, documentation, log messages and deny-lists are rejected. What is held back stays in the audit trail with the reason.

03 · alphaDecide what matters

Ranks each finding by how exposed it is and how long the data must stay secret, and says what to replace it with.

Features

From a list of findings to a finished migration

Finding the cryptography is the first step. These features turn the list into work your team can plan, check and prove.

  • How to fix it, where it was found

    Each finding says what to replace it with in that language, library or config file: the JDK, Go, .NET or OpenSSL call, or the nginx and sshd line.

    report.html, SARIF help
  • Policy and deadlines

    Checks the scan against NIST IR 8547 or CNSA 2.0, or your own rules, and lists what is overdue and what falls due next.

    --policy nist-ir-8547
  • Used or only declared

    An algorithm the code calls is marked apart from one that only appears in a list of supported names, so you fix the calls first.

    wolfpack:usage
  • One view of the organisation

    Merges the scans of every system into one inventory and dashboard: weakest systems first, and where each algorithm is used.

    wolfpack merge
  • Progress over time

    Each merge can be added to a history, so the dashboard charts the quantum-safe share and the policy breaches run by run.

    --history runs.jsonl
  • Fast checks on every pull request

    Scans only the files changed since a branch, and fails the build only on cryptography that is new since the last release.

    --changed-since main
  • An audit trail

    Everything the scouts found is kept with the evidence and the reason it was accepted, held or rejected.

    findings.json
  • Silence what you have checked

    A wolfpack:ignore comment on a line, or an exclude pattern, keeps a reviewed finding out of later runs.

    .wolfpack.toml

Running it

Run it where your code already is

One command and one runtime dependency, on Windows, macOS and Linux. It opens network connections only to the endpoints you name.

On a laptop

Python 3.11 or newer.

wolfpack scan ./payments-api

In a container

Mount the folder; the results land beside it.

docker run --rm \
  -v "$PWD:/scan" wolfpack

In GitHub Actions

Findings show up as code scanning alerts, and the build can stop on new problems.

with:
  fail-on: critical

Set it up once

A .wolfpack.toml in the repository keeps every run the same: what to skip, when to fail the build, which servers to probe, and how long your data must stay secret.

Against a baseline, only cryptography added since the last release fails the build, so an existing backlog does not block every merge.

exclude    = ["generated", "*.min.js"]
fail_on    = "high"
shelf_life = 15     # years the data stays secret
migration  = 6      # years your migration takes
tls        = ["api.example.com:443"]

[policy]
profiles = ["nist-ir-8547"]

More ways to use it

Every command writes the same four outputs, so they combine: scan each system, then merge the results into one dashboard.

wolfpack scan app-image.tar          # a saved container image
wolfpack scan --pcap gateway.pcap    # handshakes from a capture
wolfpack scan --tls api.example.com:443 --ssh bastion.example.com
wolfpack merge scans/ --name "Example Bank" --history runs.jsonl

Limits

Good to know

Every finding carries its evidence and a confidence, so you can see why it is there. These are the cases where you should look twice.

  • Python is fully parsed. Other languages use rules: names passed through one function or joined from literals are followed, but values that travel further, or come from input at runtime, can be missed.
  • Cryptography written by hand, with no library call or algorithm name, is found only when it uses a well-known constant.
  • An algorithm found in a binary is built into it, which does not always mean it is used.
  • A traffic capture shows only the handshakes it contains; TLS 1.3 hides the server certificate, so capture a live probe too.
  • Fixes name the first library releases with the feature. Check them against the versions you can deploy.
  • The year a quantum computer could break RSA is an assumption you set, 2035 by default, not a prediction.
